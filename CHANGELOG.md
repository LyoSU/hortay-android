# Changelog

[Keep a Changelog](https://keepachangelog.com) · [SemVer](https://semver.org). One user-visible change per bullet; rationale lives in commits, not here.

## [Unreleased]

### Changed
- Channel navigation is now "wait-for-content" instead of "instant-transition-with-skeleton". On every tap that opens a channel (in-app chip, Channels-tab row, deep-link, cross-channel reply-quote, ChannelScreen → ChannelScreen reroute) the push site runs `PostsRepository.primeChannelForOpen(chatId)` with a 300 ms grace — for channels the merged feed has already touched the call returns instantly from `_posts`, for cold-cache channels `loadChannelHistory` typically completes inside the window. Either way the target `ChannelScreen` mounts with its slice already populated, so the LazyColumn paints `Ready` in its first frame instead of running a transient skeleton state at all. The single-flight contract on `loadChannelHistory` (`deepLoadJobs.computeIfAbsent`) means the launched preload IS the same Deferred `ChannelViewModel.init` awaits — no second `GetChatHistory` round-trip. When 300 ms elapses without a slice landing the push proceeds anyway with a `preloadTimedOut = true` flag on the `NavEntry.Channel`; the target screen reads it and skips its own 600 ms `rememberDeferredLoading` grace — paints the skeleton on the first Resolving frame instead. Stacking the source-side wait with another target-side grace would surface as a freeze ("tap, then ~900 ms blank") which is worse than the iOS-style "tap → brief hold on source → skeleton if it really is slow". The 300 ms window matches the perception threshold Apple HIG calls "noticeable but not yet a lag" — the same threshold Telegram-iOS uses for its channel-cell-to-conversation animation.

### Fixed
- Returning from a channel back to the feed no longer "throws the user onto" a different post when an album-tailed channel finished hydrating in the background ("пости старі з каналу підгружаються і в стрічці думають що це новий пост і кидає на нього при поверненні"). The previous `preserveReady`-while-overlay fix kept the feed's `items` frozen until the user dismissed the overlay; on dismissal items adopt the live candidate in one batched [LazyColumn] reconciliation, and Compose anchors the visible viewport on the saved `firstVisibleItemKey`. That contract held for ordinary posts but broke for one specific shape: a channel whose cold-start `Chat.lastMessage` was an album member AND whose `coalesceAlbumFragments` surround-fetch failed (FLOOD_WAIT, transient network, message aged out of TDLib's local store) rendered a 1-fragment card with `post.id = lastMessage.id` — typically the HIGHEST album member id, since TDLib stamps `lastMessage` as the most recent message and album siblings are sent sequentially. When the user opened the channel, [PostsRepository.loadChannelHistory] returned the full album; [foldRawIntoCurrent] + [PostFilterStrategy.mergeAlbumMembers] rebuilt the card with `anchor.id` = the LOWEST member id (intentional and load-bearing — per tdlib/td#2312 only the first message of an album carries `replyInfo`/`reactions`, and the lowest id is stable across the interaction-info update stream). With `FeedItem.Single.key = "post_${chatId}_${post.id}"` that anchor flip changed the row's key from `"post_X_<high>"` to `"post_X_<low>"`. Compose's [LazyColumn] couldn't find the saved `firstVisibleItemKey` in the new list, fell back to the raw `firstVisibleItemIndex`, and the user saw a different post at their viewport top — one of the newly-folded older history rows that happened to land at that index, reading exactly as "feed thinks it's a new post and lands me on it". `FeedItem.key` now keys album posts on `(chatId, mediaAlbumId)` — both the 1-fragment cold-start card and the rebuilt full-album card share one row identity, so the scroll-anchor survives the rebuild. `mediaAlbumId` is per-session client-side state but `LazyListState.Saver` only persists raw index+offset across process death, so we never need it to be globally unique — only stable for one process lifetime, which it is. Standalone (non-album) posts continue to key on `post.id`, and the existing thread-reshape stability (`Single(reply) → Thread(parent, reply)` keeping the reply's key) is unchanged.
- Poll voting now actually goes through instead of flashing a `(406)` error every time and reverting the chosen row ("не працює голосування в опитуваннях, 406 помилка пише завжди"). The optimistic flip → `SetPollAnswer` RPC → revert-on-failure path treated every non-zero TDLib code as a real error: code `406` fell through `TdErrorMapping`'s `else` branch as `TdErrorKind.Unknown`, the snackbar painted `Не вдалося проголосувати в опитуванні (406)`, AND `ChannelActionsRepository.setPollAnswer` returned `false` → `clearPollPending(revert = true)` rolled the chosen-row chip back. But per TDLib's documented `error` class (`core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1error.html`): "If the error code is 406, the error message must not be processed in any way and must not be displayed to the user." TDLib uses 406 as a **client-side silent-no-op sentinel**, conceptually adjacent to HTTP `304 Not Modified` — it fires when the local poll mirror already matches the requested selection (or when TDLib's poll cache is mid-resolve), and the authoritative state arrives moments later via `UpdateMessageContent`. So we were (a) displaying an error TDLib explicitly forbids displaying, and (b) reverting an optimistic flip that was actually correct, making every poll tap look like a failure even though the server-side vote was either in flight or already counted. New `TdErrorKind.Silent` classifies code 406 and `surfaceTo` drops it before reaching `UserMessageBus` — uniform behaviour across every TDLib call (mute / leave / report / etc., the spec is global). `ChannelActionsRepository.setPollAnswer` and `toggleReaction` (same optimistic-revert shape) additionally promote a 406 outcome to `Boolean = true` via a new `Throwable?.isTdSilent()` helper, so callers don't roll back optimistic UI on a TDLib-internal no-op — the eventual `UpdateMessageContent` / `UpdateMessageInteractionInfo` is the authoritative source for the chip's final state. Regression locked by `TdErrorMappingTest` (kind classification + non-emission through the bus + helper truth table).
- Channel cards no longer "ride in" one frame after channel entry ("карточка пост появляється з затримкою, спочатку біле"). `rememberLatchedChannelUiState` was initialising its `mutableStateOf` to a static `ChannelUiState.Resolving` sentinel and overwriting it from the [LaunchedEffect] block — but [LaunchedEffect] dispatches on commit, AFTER the composition that returned the latched state. So even when the upstream pipeline (`primeChannelForOpen` preload + the `ChannelViewModel.posts` StateFlow's synchronous initial value) had already produced a Ready candidate, the latch returned Resolving on the first composition. [ChannelScreen]'s render gate then fell through to its blank-during-resolve branch — the Scaffold's surface colour painted under an empty body for one frame, then the LaunchedEffect ran on the next frame, the latch caught up, and the LazyColumn paints over the white. Visible on every channel entry. The latch now seeds its initial value from the first `candidate` it receives — Ready becomes a frame-one state when the upstream is warm. The LaunchedEffect keeps doing its job on subsequent emissions; `reduceChannelUiState`'s Ready→Ready branch preserves the latched initialIndex exactly as before.
- Opening a channel no longer paints a frame of empty Scaffold background ("спочатку біле бачу, а потім з'являється пост") before the LazyColumn materialises. `ChannelViewModel.posts` is a `StateFlow` built via `repo.posts.map { … }.stateIn(viewModelScope, SharingStarted.WhileSubscribed, persistentListOf())` — `WhileSubscribed` only activates the upstream map when something actually collects, which doesn't happen until [ChannelScreen]'s first `collectAsStateWithLifecycle()` call lands. So the very first composition reads `posts.value = persistentListOf()` even when the wait-for-content preload (`primeChannelForOpen`) had just populated `_posts` with a real slice for this chatId moments before the push. `buildChannelUiState` then took the empty-items branch → `Resolving` → the Scaffold rendered its surface background under a blank body, and the user saw a one-or-two-frame white flash before upstream emitted the actual slice and the LazyColumn painted over it. The initial value is now seeded SYNCHRONOUSLY from `repo.posts.value.filter { it.chatId == chatId }` at VM construction time — so the first composition reads the same slice the preload populated, `buildChannelUiState` returns `Ready` immediately, and the LazyColumn paints posts on frame one with no white intermediate. WhileSubscribed continues to gate upstream collection (no work runs while ChannelScreen is unmounted), only the synchronous read at construction changes.
- Channel entry no longer flashes a skeleton placeholder on fast opens ("скелет при відкритті каналу швидкому все одно є"). The `Resolving → SkeletonFeed` render gate fired the instant [ChannelUiState] entered Resolving — so the skeleton painted for one or two frames every time a channel's history resolved in under ~100 ms (the common case for any channel TDLib serves from its local cache, which is most of them once a session is warm). The skeleton's own shimmer animation kicked in just as Ready took over, so the user saw it crossfade through `nothing → skeleton with shimmer → real posts` in <200 ms — a flicker even though every intermediate state was correct. Gated through the existing `rememberDeferredLoading` helper (same 600 ms `LOADING_OVERLAY_GRACE_MS` the comments overlay and media indicators already use), so fast resolves render `header → blank for a frame → Ready` with no skeleton in the middle, while slow resolves (deep-link cold-cache, FLOOD_WAIT, post-DC migration) still surface the full skeleton past the grace threshold where the user genuinely needs feedback. One app-wide threshold for "slow enough to surface" — same contract that gates the comments overlay's loading spinner and the media loading discs.
- Returning to the feed from a Comments → ChannelScreen drill no longer lands the user at the start of the feed instead of the row they were on before the overlay opened ("свайп назад, потрапляю просто в стрічка ще й на самий початок"). [TimelineScreen] is rendered inside [TabContentSwitcher] with a stable `SaveableStateProvider`, [NavOverlayRenderer] mounts Comments / ChannelScreen on top, and `selectedTab` stays `Feed` throughout the round-trip — so the feed never unmounts and `LazyListState.Saver` cannot lose its bundle. The reset wasn't a remount: it was the LazyColumn UNDERNEATH the overlay reconciling a regrouped keyed dataset. [ChannelViewModel] eagerly issues `loadChannelHistory(chatId)` on init, which writes the deepened slice into the same global `_posts` flow [TimelineScreen] is subscribed to. The downstream candidate built by [buildTimelineUiState] therefore arrived at the latcher as a fresh `Ready` with a regrouped `items` list — a reply parent surfaced by the deep-dive could promote a `FeedItem.Single` row into a `FeedItem.Thread` member, and new arrivals in Newest mode shifted indices. [reduceTimelineUiState]'s `preserveReady` guard only blocked `Ready → Loading/Empty` (the "don't show a skeleton because we're momentarily empty under overlay" case) — it let `Ready → Ready` pass straight through and overwrote `items`, so the LazyColumn under the overlay reconciled the new list. When the previously-first-visible key vanished through regrouping the scroll relayouted off-anchor; the user saw it on overlay pop as "back lands at the start". The fix tightens `preserveReady` to freeze the latched `Ready` in full — any `Ready → Ready` transition under overlay is a no-op, no `items` update, no `frozenCursors` re-latch. On dismissal `preserveReady` flips false and the next live emission flows through the existing Ready→Ready branch normally — `items` adopt the live candidate's list in one batched update from the user's actual scroll position. Mirrors the parallel "read-acks pause under overlay" contract (`markAsRead = null` in [TimelineScreen]) — same "feed is frozen while user is elsewhere" principle, now applied to data as well as side effects.
- Channel header subscriber count now appears on the very first frame of channel entry instead of a beat after the title ("якось з затримкою кількість підписників показується"). `PostsRepository.channelSubscribers()` issued two sequential TDLib RPCs (`GetChat` + `GetSupergroup`) on every channel open — and although TDLib serves both from its local cache in steady state, those calls still suspend until the daemon's reply scheduler picks them up, which left the `ChannelHeaderBar` subtitle painting `null` for one composition before recomposing with the resolved count. `UpdateSupergroup` (which carries the live `Supergroup.memberCount`) was already streamed to the repo on session warm-up — but the listener only invalidated the message-mapper's username cache and discarded the rest of the object, so a perfectly fresh memberCount sat in a TDLib update we threw away. Now the listener mirrors the full `TdApi.Supergroup` into a new `supergroupCache: ConcurrentHashMap<Long, TdApi.Supergroup>` (same shape as the existing `chatCache`), a new synchronous `channelSubscribersCached(chatId)` reader composes the two mirrors (`chatCache → supergroupId → supergroupCache → memberCount`), and `ChannelViewModel.channelSubscribers` is seeded from it in the VM's property initialiser — **before** the first composition collects the StateFlow. So for every channel that has surfaced in the merged feed at least once this session (the common case for every non-deep-link entry point, since `UpdateSupergroup` is emitted for the entire local cache on session warm-up), the subtitle paints with the count on the very first frame. Cold-cache fallback (deep-link into a never-seen channel, freshly joined channel whose `UpdateSupergroup` is still in flight) still goes through the suspend `channelSubscribers()` variant which now skips the redundant `GetChat` when the cached `Chat` already yielded the `supergroupId`. `PostsRepository.clear()` wipes both mirrors so account-switch can't surface the previous account's subscriber count on a same-named channel.
- Inline videos and GIFs in the feed no longer briefly stretch to fill their parent slot on autoplay mount before snapping to the correct aspect ratio one frame later. `TdVideoPlayer` accepts an `initialAspect: Float` seed for [AspectRatioFrameLayout.setAspectRatio] specifically to letterbox the texture on first layout — `FullScreenMediaViewer` was passing it, the inline feed call sites in `PostBody` were not. Without the seed, `AspectRatioFrameLayout` filled its parent until ExoPlayer's `Player.Listener.onVideoSizeChanged` fired (50–500 ms after mount, depending on how fast the decoder reads the file headers), at which point the texture re-laid out to its real ratio — visible as a brief stretch-then-snap on every autoplay scroll-into-view, doubly visible on portrait videos where the snap was the most extreme ("відео не одразу правильного розміру одразу і блимає коли змінює свій розмір"). The poster's `TdMedia.width`/`height` were already in memory from the message mapper — they ARE the playback geometry for ordinary videos, since TDLib delivers the same dimensions on the original message content and the encoded stream. Threading them through as `initialAspect` (via a new computed `TdMedia.aspectRatio` property that returns the conventional `0f` sentinel for missing dimensions) makes the first frame land at the correct size. Applies to both the inline-autoplay video card and the animation/GIF card; the fullscreen viewer already had this fix and is unchanged.
- Opening a channel from the feed (or anywhere else in-app) no longer flashes a skeleton placeholder for a frame before the real posts paint, even when the channel's posts were already cached locally. `ChannelViewModel` always issues `loadChannelHistory` on init to deepen the per-channel slice past the one-post-per-channel coverage that the merged feed's cold-start harvest provides — `_historyLoading` stays `true` until that TDLib round-trip completes. `buildChannelUiState` was treating `historyLoading == true` as an unconditional `Resolving` gate, so even when `repo.posts` already had this channel's slice populated (the common case for any channel that appeared in the user's home feed) the LazyColumn stayed hidden behind `SkeletonFeed` for the duration of the round-trip, then crossfaded to the real list in a single frame — exactly the "skeleton блимає навіть якщо швидко прогружаються" symptom. The gate now requires `items.isEmpty()` as well: when the slice already has content, the channel renders immediately and the deeper history merges in via the live `posts` flow as it arrives. Deep-link landings keep their own correctness gate (the `scrollToMessageId` branch still returns `Resolving` until the target message is in `items` OR `attemptedAround` flips true, so we never paint a wrong-index `Ready` on the way to a deep link).
- Channel top-bar title no longer jumps upward the moment the subscriber count loads. `ChannelHeaderBar` rendered the subtitle `Text` conditionally on `subtitleText != null` — until `ChannelViewModel.channelSubscribers` resolved (one TDLib `chatSubscribers` cache hit per channel entry), the title `Column` had a single child and the M3 Compact `TopAppBar` (64 dp) centred it vertically inside its 64 dp slot. The instant the count arrived a second `Text` appeared below, the `Column` measured taller, and `TopAppBar`'s vertical-center repositioned the title upward — visible as a small but jarring shift on every channel open ("назва по центру а потім зміщається через це"). The subtitle slot is now always rendered (`subtitleText.orEmpty()`); an empty `bodySmall` `Text` still reserves one line of height, so the row's intrinsic height is constant across the null → resolved transition. Applies to both TDLib mode (`ChannelScreen`) and guest mode (`WebChannelScreen`) since they share the helper.
- Snap-scroll mode (Settings → Feed → "Snap scroll") no longer makes tall posts unreadable, and now feels predictable on gentle flings. The previous implementation passed `SnapPosition.Start` to `rememberSnapFlingBehavior` — the Reels / fixed-size-paginator idiom, which is actively user-hostile on a mixed-height feed. Three failure modes were stacked:
  - **Tall posts couldn't be read mid-way.** A post bigger than the viewport had no settled scroll position other than its top: any micro-fling started from inside it snapped either back to its top or forward to the next post's top. There was no way to pause two paragraphs in. The MDN and CSS-Tricks pages on `scroll-snap-type: mandatory` both call this out as the canonical anti-pattern for variable-height content.
  - **"Snap-back" on gentle flings made forward swipes feel resisted.** The stock `rememberSnapFlingBehavior` runs an approach-decay phase first, then snaps to the *nearest* item to the decayed landing position. A forward fling whose decay undershot the next post's top would land back on the current post's top instead — reading as "the scroll grabbed me back". Reproducible on every fling soft enough that decay distance < (viewport − scrolled-distance-within-current-item).
  - **Hard flings overshot multiple posts.** Default snap-fling has no upper bound on how many items a strong fling can span — fine for Reels (every item is the same height), jarring for a feed where each post is a deliberate stopping point.

  Snap-fling is now routed through a new `rememberFeedSnapFlingBehavior` that implements the discrete-swipe / paginator model — the same idiom Instagram applies to its main feed (one-post-per-swipe; "scroll stops on the next post and you have to scroll again"). A custom `SnapLayoutInfoProvider` returns 0 from `calculateApproachOffset` (collapsing the algorithm into a single decisive snap animation, no decay-then-target-pick) and computes `calculateSnapOffset` from the velocity sign and the *current anchor post*: forward velocity → next post's top, backward velocity → either the anchor's top (if we've scrolled past it) or the previous post's top. On a tall post the forward branch falls back to "scroll anchor's bottom edge to viewport top" — the page-down idiom: a strong fling inside a long post advances exactly one viewport's worth of content, not three or four posts past it, and the very next fling commits the actual next post the moment it enters the visible-items window. The only fallthrough to `ScrollableDefaults.flingBehavior()` is below an initial fling velocity of 400 dp/s, so soft drag-releases settle naturally as position nudges (gentle reading, fine-grained positioning) instead of being grabbed by a snap animation. Snap resumes on the next intent-level fling. Drag scrolling stays free regardless — only the fling animation is affected. The snap-scroll contract is now uniform: one fling = one logical step, regardless of fling strength or whether the anchor fits the viewport. Mirrors what Instagram's main feed gets wrong (no upper bound on fling reach in long carousels, hence the persistent "how to disable snap scrolling" complaints from users who skid past content) while keeping the "click into place" feel for the common case.
- Feed scroll position is now preserved across tab swaps (Home ↔ Channels ↔ Settings ↔ back to Home) even when read cursors moved while the user was on another tab. Previously, `rememberSaveable(routeKey, readySeed, saver = LazyListState.Saver)` keyed the saver bundle on the LIVE boundary index — so a user who scrolled to row 100, switched to Channels, dwelled there long enough for new posts to arrive (boundary moved from B to NEW_B), and returned to Home was greeted with the LazyColumn freshly seeded at NEW_B instead of restored to row 100. Compose's `LazyListState.Saver` already persists `firstVisibleItemIndex` + `firstVisibleItemScrollOffset` natively across composition removal — the bug was that we were re-keying the saver bundle every time the boundary moved, which Compose interprets as a fresh slot. The fix pins the cold-start seed at the first Ready transition via `rememberSaveable(routeKey) { mutableIntStateOf(-1) }` so it survives tab swaps and process death with the same lifecycle as the `LazyListState` itself — subsequent boundary movements no longer poison the saver key. Same fix applied to `ChannelScreen` (drill-out → drill-in within a single feed visit now preserves channel scroll even when the channel's own cursor advanced). Cold-start "first paint at the correct row in one frame" guarantee is preserved — the candidate boundary is read via a `?:` fallback before the side-effect-driven pin lands, so the very first frame of a fresh route already keys on the correct seed.
- Reverse-feed (`OldestUnreadFirst`) no longer lands cold-start on an ancient post — typically a years-old broadcast from a dormant channel, or the latest post from a channel where the user is the admin/creator. Two compounding root causes were fused into one bug:
  - `cursorsHaveLanded` flipped true the moment the **first** `UpdateChatReadInbox` landed (`map.isNotEmpty()` in `CursorHolder`). The boundary picker then ran against a **partially seeded** cursor map: chats whose `UpdateNewChat` hadn't been processed yet had `cursor == null` and looked "read" per `isUnreadIn`, so the first `Ready` snapshot pinned the LazyColumn at an arbitrary row. The `rememberLatchedTimelineUiState` reducer's "preserve initialIndex across Ready→Ready" contract then froze that wrong landing for the rest of the session — even though the cursor map filled in normally a few hundred ms later. Gated now purely on `refresh idle + COLD_START_CURSOR_GRACE_MS`: refresh's own `drainChatList` + `awaitAll` are downstream of the same `UpdateNewChat` burst that seeds the cursor map, so by the time `refreshing` falls true → false the map is as complete as TDLib will deliver it for this cold-start window. The grace covers in-flight `UpdateChatReadInbox` deltas the daemon sends right after `LoadChats` resolves.
  - `refreshLocked` harvested `Chat.lastMessage` for **every** chat in `ChatListMain`, including chats with `unreadCount == 0`. In the asc-by-date sort that powers `OldestUnreadFirst`, the oldest of those caught-up `lastMessage`s — typically a 2017 post from a long-dormant subscription — sat at `items[0]` and read as "where you left off" even when it was technically read. The admin-owned channel variant is the same shape with a different cause: TDLib tracks inbox and outbox read state separately (`lastReadInboxMessageId` vs `lastReadOutboxMessageId`), and for own-channels `lastReadInboxMessageId` can stay at 0/stale while outbox is high (cf. tdlib/td#1419) — our cursor-based "is it unread?" heuristic (`post.id > cursor`) is unreliable in that case. Switched to TDLib's server-authoritative `Chat.unreadCount`: cold-start harvest skips chats with `unreadCount == 0`, so caught-up dormant channels and admin-owned channels stop polluting the reverse-feed landing window. Live `UpdateNewMessage` arrivals are unaffected — this is purely a cold-start initialisation filter. Snapshot restore is also unaffected (covers the "I read everything in another client" case where the feed would otherwise look empty on the next launch).

  Cleanup ride-along: dropped the unused `cursors: ReadCursors` parameter from `List<TimelinePost>.orderedFor()` — the sort is strict asc-by-date and never peeked at the map; the parameter had been carrying `@Suppress("UNUSED_PARAMETER")` for several releases.
- Albums no longer render incorrectly inside the comments overlay. Two compounding bugs were merged in one place — both surfaced as "альбоми в коментарях не працюють правильно":
  - **Root-album mirror leaking as phantom comments.** When the channel post itself is an album (the common case for any photo/video collage), TDLib mirrors it into the linked discussion supergroup as N messages with the same `mediaAlbumId`, all sharing `topicId = MessageTopicThread(rootId)`. The bootstrap pagination loop's `seenIds.add(anchor.rootId)` filter excluded *exactly one* of those N ids; the remaining (N − 1) album siblings landed in `live` and rendered as if they were ordinary user comments above the actual discussion. Visible on every album post that has comments enabled. The fix captures `rootAlbumId` lazily during pagination (scanning the whole batch first, since `GetMessageThreadHistory` walks id-desc and the canonical lowest-id mirror appears *after* its higher-id siblings in the batch iteration order) and excludes every message with that `mediaAlbumId` from `live`. The same filter is applied to live `UpdateNewMessage` deliveries so reconnect re-emissions stay no-ops.
  - **Albums posted AS COMMENTS rendering as N stacked single-photo bubbles.** A user (or admin) posting an album of photos in a discussion thread used to land as N separate `ThreadRow`s, because `CommentsRepository.buildTree` mapped each `TdApi.Message` 1:1 with no `mediaAlbumId` grouping. The caption appeared on only one of them (Telegram pins it to the canonical lowest-id member per `tdlib/td#2312`); reactions / reply-info appeared on only one (same TDLib invariant — `interactionInfo` is filled only on the first album id); the row order across re-renders was non-deterministic because every member shared the same whole-second timestamp. `buildTree` now routes mapped posts through `PostFilterStrategy.mergeAlbums` (the same helper the feed uses — promoted from `private` to `internal` for cross-package reuse). After merge, replies that point at a mid-album member id (Telegram-UX reroutes "reply" to the canonical member, but the server-side API accepts any sibling) are reparented to the merged anchor through a `memberId → anchorId` redirect map, so they don't collapse to depth 0 with an orphaned parent reference.
- Tapping the "↓ N" unread-remaining pill no longer skips every second post. Two compounding bugs were turning the pill into "jump-by-two":
  - `rememberReadAckDwell` was reading viewport state from `LazyListLayoutInfo.visibleItemsInfo`, which by design includes any item that overlaps the viewport by even one pixel. After `smartScrollTo` landed the target row X at the top, the next row X+1 was already partially poking up from the bottom edge — fully within `visibleItemsInfo` per Compose semantics, but the user had only seen a sliver of it. The 1-second dwell timer happily ran on X+1, `viewMessages(forceRead=true)` fired for both, and the next "↓ N" tap resolved the first still-unread row to X+2 instead of X+1.
  - Even items that became fully visible mid-drag could satisfy the dwell window if the viewport stayed stable enough for a second while the user was *still actively scrolling* past them. Mirrors Telegram-Android's own `SCROLL_STATE_IDLE` gate before `messages.readHistory` and Twitter's own "stable for ≥1s while not moving" impression rule.
  The dwell now requires (a) the item bounds to sit entirely inside `[viewportStartOffset + beforeContentPadding, viewportEndOffset - afterContentPadding]` *and* (b) `LazyListState.isScrollInProgress == false`. The `contentPadding` subtraction is what makes the check **actually** match what the user sees: Compose's `viewportEndOffset` does **not** subtract `afterContentPadding` (items render through the padding zone during scroll), so without trimming it ourselves a post whose bottom edge has scrolled into the floating bottom NavBar's reserved slot would still satisfy strict containment and get acked — same off-by-one symptom, just on a different set of rows. Posts taller than the (now-tight) viewport get a fallback ("dominates ≥50% of the user-visible area") so long-form posts still get marked read — strict containment would otherwise never fire for them. Applies to both the merged feed (`TimelineScreen`) and the per-channel screen (`ChannelScreen`) since they share the helper.

### Added
- Round video messages (Telegram's "video note", `messageVideoNote`) now play inline in the feed as a circular bubble with full Telegram-parity chrome — progress ring around the perimeter, live remaining-time chip (`-0:08`), tap-to-pause / resume with a centred play glyph that fades in on pause, and an independent volume chip at the top-trailing corner that toggles audio without affecting play state. Silent autoplay on viewport entry, looped — the same idiom Telegram uses in chats and channels. The bubble owns its own pooled `ExoPlayer`, polls position at 100 ms while playing (500 ms while paused — no point waking the dispatcher to read the same number ten times a second), and survives the mute toggle's pool swap via a saved playhead so the audio toggle is perceptually seamless. Re-keying the player on `muted` is the only way to flip it cleanly: the pool acquires *muted* players without an audio renderer at all (`ExoPlayerPool.acquire(muted = …)` constructs the player without an AudioTrack so silent inline videos don't hold an audio focus wakelock), so a runtime `setVolume(1f)` on the muted instance would be a no-op. Both regimes stay warm in the pool so the toggle costs about the same as a normal scroll-into-view acquisition. The mute chip's clickable nests inside the bubble-wide pause clickable — Compose pointer hit-testing dispatches to the innermost interactive node first, so a tap on the chip never doubles as a pause. Honours the same auto-download contract as long-form inline video: only files the user's policy already pulled to disk autoplay (`isCachedReady` gate), and only when Settings → Feed → "Autoplay videos in feed" is on — otherwise the bubble shows the same centred `play_arrow` affordance as a not-yet-autoplayed video, and tapping it routes to Telegram. - Guest-mode background polling now runs only when the user is actually in guest mode AND the app is foreground. The previous gate only checked "not signed in to TDLib", which kept the t.me/s/ poller alive on the auth screen — burning traffic and battery for a UI that doesn't even render the web feed, with a real CDN-side FLOOD_WAIT risk.

### Fixed
- Guest (web) mode: fullscreen viewer Save / Copy / Share buttons no longer silently vanish on posts whose bytes never reach TDLib. Photos route through Coil's on-disk cache (the same bytes the inline poster + fullscreen variant already painted from) — Save / Copy / Share all use the local-file pipeline, no re-download. Web-mode videos / animations get a Share button that falls back to `text/plain` ACTION_SEND with the CDN URL so recipients still receive a clickable link.
- Fullscreen photo viewer: double-tap to zoom **out** (second tap while zoomed) now actually fires. The pinch handler used to consume every event while `scale > 1×` — including the stationary second tap of a double-tap — which starved the tap detector before it could complete the gesture. Pinch handler now only consumes when there's actual movement (pan or zoom delta), so stationary taps on a zoomed photo pass through to the tap detector and double-tap-back works.
- Guest mode: the floating "↓ N" unread chip is no longer obscured by the "Add channel" FAB on the Feed tab. Both are bottom-end anchored; the pill now stacks above the FAB so it stays tappable while unread posts remain.
- Tapping the centre play button on a video that has played to the end now restarts it from the beginning instead of being a dead tap. ExoPlayer's `play()` is a no-op when position is past `duration`, so the chrome's onClick now special-cases `STATE_ENDED` with a `seekTo(0)` before resuming — matches the canonical YouTube / Telegram "replay" behaviour. Looping videos (≤ 60 s clips) handle this automatically via `REPEAT_MODE_ONE`; this branch covers finite-playback videos in fullscreen.
- Short videos (≤ 60 s) now loop in the fullscreen viewer too, matching the inline-feed autoplay threshold. Previously a clip that looped silently in the feed stopped at the end on fullscreen-tap and required a manual replay tap. Longer videos keep finite playback so the scrubber rests at the end and exiting the viewer doesn't restart playback in the background.
- "↑/↓ N нових постів" pill no longer lands the user on the post immediately BEFORE the just-accepted batch. Two stale-state hops compounded on this path: (1) the `feedItems` captured by `onClick` was the PRE-ack snapshot, and (2) even after switching to the live `feedItemsState`, the LazyColumn's actually-laid-out item count lags one Compose frame behind because `TimelineUiState.Ready.items` is latched through a `LaunchedEffect` — `scrollToItem(N)` then clamped N down to the OLD `lastIndex`, i.e. the row right above the new arrivals. The handler now waits (capped at 800 ms) for `listState.layoutInfo.totalItemsCount` to grow past the pre-tap value — that's downstream of BOTH staleness hops and the same number `scrollToItem` clamps against — then scrolls to the FIRST of the just-accepted posts so the user reads the new batch top → down (canonical Telegram / Slack / Discord "New messages" jump). `UnreadCounterPill` shares the live-read path for staleness safety even though it does not trigger an ack.
- Tapping an inline reply / quote card on a post no longer scrolls and highlights the post underneath in the feed. Feed: the freshly pushed `ChannelScreen` lands at the replied-to message and pulses the highlight there; the feed itself stays still. In-channel cross-channel replies now also pass the target messageId through to the new channel screen — drilling into a different channel from a quote tap lands at the replied-to post instead of opening cold at the newest message. Polls expose the question; checklists expose the title plus `[x] / [ ]` task lines; audio exposes title + performer; documents fall back to the filename when no caption was authored.
- Post-card "Report" action shows a moderation glyph instead of the silent help question-mark fallback. Bundle a dedicated `sym_flag.xml` when convenient — current mapping is `shield`.
- Reaction chips on the post-detail anchor and on comments now actually toggle; the anchor PostCard tracks the live feed entry so optimistic updates and server `UpdateMessageInteractionInfo` flow into the visible chip.
- Fresh posts reach `OldestUnreadFirst` feed without restart.
- Cold-start scroll-pin no longer fires on mid-session arrivals.
- Photo albums no longer ship with missing members on slow networks.
- Cold start waits for the fresh feed and only falls back to the cached snapshot when refresh fails — no more visible top-of-feed content swap mid-load.
- `OldestUnreadFirst` no longer auto-scrolls to the bottom on cold start when read cursors haven't loaded yet.
- `OldestUnreadFirst` no longer flashes a random ancient post as the first visible card on cold start; falls back to newest-first until read cursors land, then re-sorts.
- Editing a caption on an album in the channel no longer collapses the card to a single photo — `UpdateMessageContent` for any album member (anchor or sibling) re-ingests the whole group instead of replacing the merged content in place.
- `OldestUnreadFirst` cold start: restore the asc-by-date reverse-feed layout (oldest read at top → unread queue → newest at the bottom, chat-app idiom) and eliminate the cold-start re-sort flash by gating the LazyColumn render on cursors-landed. The column shows nothing until TDLib's first `UpdateChatReadInbox` burst arrives, then paints in one stable transition with the scroll already positioned at the read→unread boundary (or at the bottom when caught up). No more "ghost old post for a beat, then jump".
- 5-photo albums whose anchor is `Chat.lastMessage` now reliably reach the feed on relaunch: the previous healthy session's saved member ids drive a targeted `GetMessage` upgrade in `restoreFromSnapshot`, which sidesteps TDLib's chat-history hydration race that the old delay-and-retry pass tried (and sometimes failed) to wait out.
- Cold-start snapshot no longer self-poisons when the user backgrounds before the album-upgrade pass lands: `saveSnapshotNow` now preserves previously-saved album siblings of any currently-degraded album, so the next cold start still has a source-of-truth to rebuild the full card from.

Switched to the caller's nullable repository argument (null = guest mode).

Stale flag now forces the upsert through.

Newest-first sort tie-breaks by id descending; `OldestUnreadFirst` and the SQLite web-mode feed tie-break by id/seq. ### Performance
- Reaction taps flip optimistically across feed / channel / post detail / comments; server reconciles via `UpdateMessageInteractionInfo`, RPC failure rolls back.
- Feed scroll jank rework. Removes per-frame work that accumulated as the
  app grew, surfacing as micro-stutter on media-heavy stretches and on
  accounts with active dwell-ack traffic. Six load-bearing fixes ship in
  one pass:
  (1) Read cursors propagate through a `SnapshotStateMap`-backed
  `CursorHolder` (not `staticCompositionLocalOf<ReadCursors>` over a
  PersistentMap). Per-key snapshot tracking — a cursor advance for chat X
  invalidates only PostCards in chat X, not the whole MainScaffold
  subtree. Was: every dwell-ack / external `UpdateChatReadInbox`
  recomposed everything under the scaffold provider, including the
  LazyColumn body.
  (2) Viewport-centre key (used for VisibleCenter download priority
  promotion) propagates as `State<Any?>` rather than a value read at the
  `items()` lambda level. Per-item `derivedStateOf` lets a centre flip
  invalidate only the two affected items instead of every visible card.
  (3) Feed `LazyColumn` now distinguishes `FeedItem.Single` vs
  `FeedItem.Thread` via `contentType`, so the reuse pool serves each
  shape from its own slot.
  (4) Per-post inline-autoplay cache probe (`isCachedReady`) runs only
  after the cheap gates (global autoplay toggle, duration, revealed,
  active, !unplayable) all pass. Was: every video card mounted a
  `StateFlow` collector + `LaunchedEffect` resync even when autoplay
  was anyway impossible.
  (5) `MediaCache.resync` from `rememberMediaBinding` is now gated on
  `LocalScrollGate.value` so flings stop firing per-mount JNI calls for
  cards that sweep through the viewport without settling.
  (6) `TdMediaImage` minithumb (with its `RenderEffect` blur GPU pass)
  drops out 280 ms after `MediaState.Ready` lands — long enough for the
  Coil 220 ms crossfade to hide the "блимок" symptom the eager-drop
  had, then ends the steady-state per-frame GPU cost on stable media.
- `TdVideoPlayer` texture attach moved from `AndroidView.update` into
  `factory`; only the aspect-ratio update stays in `update`. The
  `exoPlayer` reference is `remember`'d per player instance, so binding
  the texture is a one-time setup — repeating it on every recomposition
  was a wasted `setVideoTextureView` call per centred-flip / parent emit.

### Architecture
- `ReactionTogglePolicy` + `PostsRepository.applyOptimisticReaction` + `CommentsRepository` per-thread override map merged into the single-collector update fan-in.
- New `TimelineUiState` and `ChannelUiState` sealed unions (Loading/Empty/Ready
  and Resolving/Ready/Missing respectively). Pure `build...UiState` functions
  derive state from already-filtered/-ordered/-grouped `List<FeedItem>` —
  scroll anchor lives in row-space, same as what the user sees. One-shot
  latching via `reduce...UiState` + `rememberLatched...UiState` keeps the
  initial scroll index stable across post arrivals and live cursor advances;
  PTR completion re-latches.
- `LazyListState` constructed once per route via `rememberSaveable(routeKey,
  saver = LazyListState.Saver)` at the resolved `initialIndex`. Cold-start pin
  loop (~80 lines of `snapshotFlow + takeWhile + scrollToItem`), channel
  cold-entry effect (~30 lines of `snapshotFlow + distinctUntilChanged`),
  scope-switch effect, feedOrder-flip effect, and inline `rememberPendingScrollToMessage`
  for deep-links all deleted in favor of the type-driven gate.

### Build
- Removed three Gradle dependencies that were declared in `libs.versions.toml` + `app/build.gradle.kts` but never imported by any source file: `androidx-navigation-compose` (project uses the in-house `NavStack` for both `MainScaffold` and `WebModeScaffold`), `compose-material-icons-extended` (project uses the in-house `Symbol` system over `painterResource(R.drawable.*)`), and `sqldelight-primitive-adapters` (`WebDatabase` is constructed without any `ColumnAdapter` — all `.sq` columns are raw `INTEGER`/`TEXT`). Lint + unit tests stay green; downstream effect is a slightly smaller R8 input and one fewer transitive `androidx.navigation.*` graph for AGP to resolve.
